# Git proof review and execution queue

Review baseline: `0368454`. The standalone object-log WAL is the product. Git
must be an ordinary, useful service that demonstrates the primitive's power
and simplicity. Passing small protocol fixtures is necessary but insufficient.
The broader proof remains open; GitHub issue #11 indexes the execution queue,
and #17 tracks the Git outcome.

## What is already sound

The inspected design has one conditional head, immutable authenticated data,
explicit uncertain publication, exact-view reads, disposable local state,
checkpoint and collection fences, and cumulative expired-view retry budgets.
The shared engine supports SHA-1/SHA-256, v2 discovery and have-aware fetch,
classic receive-pack, thin normalization and strict Git validation. Both memory
and local MinIO evidence exist; live AWS evidence is separate. The old native
engine and HTTP host are removed, while installed Git remains the reference.

Independent reviewers examined generic WAL publication/recovery, Git protocol
and ref behavior, and catalog/compaction architecture. Sidebar workers reviewed
large-pack buffering and the actual Spin operator flow. Findings below distinguish
bugs, restrictive first-proof policies, measured limits, and proposed API work.
This is not a claim of exhaustive security or formal verification.

## Why these findings matter

`read_commit_optional` used the global commit maximum despite an authenticated
reference length. This is corruption hardening: a misbehaving backend response
could allocate beyond a consumer's declared-length reservation. It is not a
claim that compliant immutable stores routinely overwrite commits.

Receive rejected an identical normalized pack even when its ref update was valid.
Deleting all advertised refs then restoring the same history can resend that
pack before GC. Input checks must remain; reuse should avoid redundant staging.

The default HEAD is hardcoded to main. Ref validation permits only UTF-8 heads
and tags, and ancestry checking always rejects branch rewrites. Those are
intentional first-proof restrictions, not complete ordinary Git workflows.
There is no receive-wire force bit: expected-old/new refs and server policy
must determine whether a rewrite is allowed.

The Spin host currently relies on externally driven test maintenance. Default
WAL tail capacity is 1,024 entries, and memory/call limits can be hit earlier.
A maintenance path is therefore necessary for sustained service, independent
of pack compaction. The first read_only host improvement is an operator policy,
not authentication or a complete deployment security model.

## Scale architecture and generic API lessons

Today catalog loading reads every live pack's full standard index and builds
an in-memory directory. Fetch graph construction starts from every ref before
selecting wants. Consequently, a tiny fetch can fail because of unrelated history.
Merging packs reduces some work but does not remove the dependence on total
repository size. Review an authenticated OID-to-location tree rooted in Git WAL
state, lazy selected-pack access, then bounded physical compaction. Keep this
catalog private to Git; it does not require a second mutable authority.
Checkpoint publication currently requires a commit in the active tail. Maintenance
after an empty-tail checkpoint needs an explicit Git maintenance WAL record or
a separately reviewed alternative through the existing head.

A copy-on-write catalog exposes actual generic friction: raw node-child references
must be recursively restaged, while same-epoch StagedObject proofs can safely
avoid redundant graph verification. Any child-proof API must authenticate its
parent proof and envelope, preserve provenance/epoch/fences, and never bless an
arbitrary ObjectRef. This is a candidate to validate, not a ratified implementation.

Other concrete friction: whole-tail materialization, duplicated CBOR node sizing,
repeated active collection-plan reads for each staged chunk, and checkpoint
rereads of already-materialized history. Git and SQLite also repeat chunked-byte
storage. Prefer small core-owned operations backed by existing proofs; extract
a byte-sequence abstraction only when the large-pack work establishes its contract.

Large capacity cannot be obtained by raising constants alone. Current full input,
decoded object, normalized pack, index-building and response buffers overlap.
Call/transfer/work quotas must evolve to account for a 1 GiB operation while
remaining finite and cumulative across retry. The 128 MiB budget is for serving
runtime, not Cargo builds, Wasmtime compilation or executable-cache preparation.

Current collection scans and materializes an entire namespace with a 100,000-object
ceiling. Retention protects the whole namespace indefinitely; crashed maintenance
needs explicit recovery and release. Scale acceptance must expose these bounds
and verify interrupted staging, compaction, concurrent pushes and GC rather
than concealing them with small fixtures.

## What makes the proof compelling

An unchanged Git client should initialize, push, clone, edit history according
to explicit policy, fetch only useful content, and operate on substantial files
and histories. A new Spin instance should recover without a local repository.
Conflicting writers must produce one winner without losing accepted updates; uncertain results must be
recoverable. Scheduled/operator maintenance must keep the system usable over
many cycles. Publish workload-specific calls, bytes, latency, memory and durable
growth with raw evidence and a reproducible demonstration.

Cursor's [Git at any scale](https://cursor.com/blog/git-at-any-scale) motivates
conditional object-storage publication and disposable replicas. Its native
local-pack design and measurements are not evidence for this direct sparse
WASI implementation. Demonstrate our own tradeoffs and benefits.

## Execution discipline and later consumers

Each implementation worker owns an exclusive worktree and bounded tranche.
Root integrates only after focused tests, independent correctness/simplification
review and applicable native/WASIp2/workspace/provider gates. Preserve memory,
filesystem-receiver, MinIO and benchmark coverage. No native server is reintroduced.
Only our GitHub tracker is authorized for routine queue updates. No upstream
reports or external communications may be published without the owner's explicit
approval of their concrete contents. Do not restore links to the withdrawn report.

After the primitive stabilizes, revisit the remote SQLite backend, production KV,
and a verifiable KV layer based on the owner's
[Geometric Search Trees research](https://g-trees.github.io/g_trees/). Those are
later consumers; do not implement them or select their data structures as part
of the present Git tranche.

## Third accepted implementation batch

Source revision `24c6ede` adds bounded ordered materialization and checkpoint
history validation, existing-only log opening, exact core-owned node sizing,
fixed-window receive scanning, and an explicit Spin rewritten-history policy.

Materialization retains a bounded read window instead of the complete decoded
tail. Parent checks and exact-view proofs remain intact. A late failure returns
no partial state; callback side effects are explicitly not rolled back.
Checkpoint validation drains the same stream before writes. Review caught and
fixed a missing-record regression that issued eight head reads instead of one.
Git's aggregate decoder reservation is still conservative; #34 stays open for
consumer accounting and long-history qualification.

`Log::open_existing` reads and validates an existing head without creating one.
`Log::node_size` shares exact encoding geometry with the node encoder; Git no
longer copies the WAL's CBOR-size formula. Oversized roots reject before chunk
PUTs, and the original small-object GC tests remain unchanged. #31 is complete.
The new receive scanner discards decoded bytes except bounded delta metadata;
whole incoming packs, normalization/index buffers and existing capacity caps
remain. #26 remains open.

Spin's `allow_non_fast_forward` defaults to false. Opt-in permits rewrites while
retaining exact old IDs, connectivity, branch types and atomic CAS. Actual
unchanged Git clients on both hashes verify default denial, successful leased
rewind, stale-lease denial, notes/custom refs, cold clone and read-only precedence.
This completes #29's ref-workflow and receive-policy scope; it is not an
authentication feature.

Independent correctness and simplification reviews passed. Combined validation

## Fourth accepted implementation batch

Source revision `86db1c2` adds authenticated child-proof traversal, the encoded
materialization read bound, and local operator status/exact commit recovery.
The accompanying Makefile change checks every Spin target/feature on WASIp2 and
adds `git-spin-operator-minio-test`; native CI already runs all workspace features.

`read_staged_node` authenticates one same-handle, same-epoch parent before deriving
its child proofs. It preserves publication/collection fences and does not create
a retention lease. Tests prove one parent GET independent of descendant count,
foreign/stale/corrupt rejection, cold uncertain-publication recovery and GC
preserving reused siblings. Independent correctness and simplicity review passed;
#33's API scope is complete. The catalog itself remains under #19.

`materialization_read_bound` returns an encoded-byte working-set bound computed
from authenticated lengths and the core's read window. It is explicitly not a
heap bound: application decoders, retained state, proofs and other operations
need separate accounting. Shared Git maintenance accounting is still in progress.

The optional native Unix `object-log-git-maintain` command opens an existing WAL
for status or resumes one exact caller-held commit token. Private inputs are
bounded, output is redacted, and timeout/lost output does not claim publication
failed. It neither listens for HTTP nor creates a second authority. Independent
review and actual both-hash Spin/MinIO command-process recovery pass.
The measured small fixtures peak below 10 MiB RSS; arbitrary cold graph resume
has not been qualified under 128 MiB. #32 remains open for that resource gap,
checkpoint/collection and sustained operator cycles.

Combined validation passes 365 ordinary tests, 14 opt-in ignored, strict native

## Fifth batch candidate: shallow clients and bounded maintenance

Candidate source `6477405` combines shallow clone/deepen/unshallow with bounded

operator checkpoint command. Independent correctness and simplification reviews
approve the shared code, including the empty-map allocation fix and core-owned

The combined candidate passes 382 workspace tests (14 opt-in ignored), strict
native and WASIp2 checks, six separately run actual-WASI lifecycle fixtures, and
the Git request audit. Raw output is in
`docs/evidence/git-proof-wave5-2026-09-05/`. The full provider gate is pending;
this batch has not been accepted or integrated into main.

Qualification exposed two separate problems. Disk exhaustion interrupted an
actual Git checkout; its raw failure is retained. Removing only inactive build
caches restored about 43 GiB. Docker subsequently stopped answering read-only
requests, and restarting that shared service requires owner approval because
other projects' containers cannot be inventoried.

Issue #37 records a test-fixture defect: stopping the Spin launcher could leave
its HTTP child and listener alive. Process-group shutdown and listener-closure
assertions are being added to Rust/Python fixtures. Provider maintenance, cold
restart, and auth-rotation evidence must be rerun with those fixes. New processes
on different ports did not prove that previous listeners were quiescent.

Issue #36 captures the remaining physical-create retry accounting gap in general
Git staging. The checkpoint fix covers its own path and does not close #36.
Catalog/cache and full-only replayable-input prototypes remain unintegrated;
versioned metadata, migration, bounded delta normalization, and real serving
callers are still required.
